### Bugs found while doing it (all pre-existing, all fixed with tests)

Removing the fake is what surfaced most of these: it agreed with the client
where the real server does not.

| Bug | Effect | Fix |
|---|---|---|
| Client instants sent as local time (no `Z`) | **Leaving a group, removing a member and archiving were always refused** and dead-lettered | `wire.dart` sends UTC |
| A page could carry entries before the member or group rows they name (a row's `seq` moves on update) | A new device paging a group whose member was renamed or claimed failed its foreign keys and could never sync it | Every page carries the group and member rows changed since the cursor; `ledger.test.ts` |
| Durable Object SQLite binds ≤100 parameters; `readEntries` bound every entry id on a page | **Any pull page with >100 expenses failed**: a device joining such a group could never sync it | Child reads chunked (`src/chunked.ts`); `ledger.test.ts` |
| Nullable `$ref`s emitted without nullability; components emitted nullable | The contract misdescribed `ChangePage.group` and friends | Components held as nullable are registered first (`app.ts`) |
| Startup revalidation racing a guest sign-in | A late "no session" answer could sign out a brand-new guest, which is unrecoverable | `_revalidate` drops an answer overtaken by a sign-in |

Also caught during the refactor: the first draft of the derived `upsertEntry`
spread the RPC argument into the insert, letting a caller set `createdBy`; the
existing roster test caught it and columns are now picked by name.

### Deploy note

The group object's migration `0000` was regenerated (the `events` table
changed shape), following the pre-release precedent of the `occurredAt`

## Summary

The overall architecture is sound and simpler than most local-first apps: one
writer per group, one integer cursor, the server computes nothing, and a real
generated-client chain that CI enforces. The Dart side does **not** have a
parallel DTO layer — it uses generated types directly, and its one
translation (`wire.dart`) is essential. Most of the complexity you were
worried about is **not** in the type chain between server and client.

Where the "define once, flow everywhere" goal does break down:

1. **Parts of the API sit outside the contract** and get parsed by hand on the
   device: event payloads (§3.1 — the generated classes exist and are
   unused), the push data payload (§2.11/§3.3), and Better Auth's
   session/guest endpoints (§3.4). That last one forces server logic
   (`toAccount`, `outcomeFor`) to be duplicated in Dart.
2. **On the server, request bodies, snapshots and closed vocabularies are
   written out again** instead of being derived from the tables and the
   `as const` lists that already exist (§1.1–1.3). The event kind → payload
   mapping appears five times across both languages.
3. **The accreted parts** are in the plumbing, not the types: a PATCH-style
   internal API kept only for tests (§2.2), ten copies of the same
   write/settle/announce boilerplate (§2.3), three stacked sync schedulers
   (§3.5), and a 694-line Dart copy of the Durable Object used for tests
   (§3.6, Q2).

Bugs found along the way (fix these regardless of the refactors):

| # | Severity | What |
|---|---|---|
| 2.1 | H, verified | A retried no-op write re-sends the *previous* change's push notification |
| 2.7 | H, per D1 docs | `inArray` lists exceed D1's 100-bound-parameter cap: `getProfilesByIds` (allows 200), the profile feed for well-connected users, and the guest sweep (batch of 500) |
| 2.8 | M, verified | A wrong email code (any Better Auth `APIError`) returns `500 internal` |
| 2.10 | M, verified in Hono source | Join and placeholders resolve the session twice |

Suggested order: bugs → §3.1 (a small change that closes the worst type
hole) → §1.2/§1.3 (vocabularies and event table on the server) → §2.2/§2.3
(object API cleanup) → the questions in §4.

Severity: **H** = structural / will keep costing; **M** = real duplication or
avoidable complexity; **L** = cleanup.

## 0. Intended architecture (as documented)

- One Worker, one origin. One Durable Object per group (sole writer, `seq`
  allocator), one FX singleton DO, D1 for cross-group index + profiles + auth,
  KV for derived blobs.
- Type chain (docs/architecture.md):
  `Drizzle tables → drizzle-zod row schemas + hand-written request bodies →
  OpenAPI → dart-dio (json_serializable) → wire.dart → Drift rows`.
- Invariants: server computes nothing (balances etc. on device); every body
  field required, null = none; calendar dates as `YYYY-MM-DD`; unknown enum
  values decode to a sentinel.

## 1. Server: schema layer

### 1.1 [M] Request/row/snapshot schemas restate the same columns by hand

`schemas/ledger.ts` derives *response* rows from Drizzle (`createSelectSchema`)
but writes every *request* body and the snapshot out field by field:

| Fact | Where it is stated |
|---|---|
| `amountMinor > 0` | `entries` CHECK, `EntrySchema` override, `EntryInputSchema`, `EntrySnapshotSchema`, `PayerSchema` |
| entry columns (kind…notes) | `entries` table, `EntryInputSchema`, `EntrySnapshotSchema`, `snapshotOf()` (events.ts), `comparable()` (ledger.ts), `columns` literal in `upsertEntry` |
| display-name rule `trim().min(1).max(100)` | `NameSchema` (ledger.ts, unexported), `ProfileUpdateSchema.displayName` (account.ts), inline again |
| `fxRate` positive | CHECK, `EntrySchema`, `EntryInputSchema` |
| timestamp overrides (`createdAt/updatedAt/…: TimestampSchema`) | once per table per column |

The docs justify hand-written bodies as "narrower than the rows they write".
drizzle-zod supports exactly that: `createInsertSchema(table, refinements)`
then `.pick()/.omit()/.extend()`. E.g.

```ts
const entryRefine = { amountMinor: (s) => s.positive(), entryDate: DateSchema, ... };
export const EntrySchema      = createSelectSchema(entries, entryRefine).extend({payers, shares});
export const EntryInputSchema = createInsertSchema(entries, entryRefine)
  .pick({ id:true, kind:true, description:true, categoryId:true, currency:true,
          amountMinor:true, entryDate:true, splitKind:true, fxRate:true,
          fxSource:true, notes:true, clientKey:true })
  .required().extend({ payers, shares, baseSeq });
export const EntrySnapshotSchema = EntrySchema.pick({...}).extend({payers: MoneyRow[], shares: MoneyRow[]});
export const GroupUpdateSchema  = GroupSchema.pick({ name:true, simplifyDebts:true, archivedAt:true });
export const MemberUpdateSchema = MemberSchema.pick({ displayName:true, upiVpa:true, leftAt:true });
```

Refinements (max lengths, regexes) live in one `refine` object per table and
apply to both row and body. Needs a check that `.required()` + nullable emits
"required, nullable" in 3.0.3 (the rule in architecture.md).

### 1.2 [M] Closed vocabularies are literal-copied across files

- `"invite" | "group_link"`: `d1/schema.ts linkTokens.kind`,
  `group/schema.ts LinkTokenWrite.tokenKind`, `LinkPreviewSchema.kind`,
  `upkeep.ts stageLinkToken(kind: ...)`.
- `"android" | "web"`: `deviceTokens.platform`, `DeviceSchema.platform`.
- `"stale" | "permanent"` (`RefusalKind`, refusal.ts) vs
  `"stale" | "permanent" | "transient"` (`RetrySchema`, common.ts).
- `["outbox","archive","purge"]` (`schedule.name`) and `type Chore` (upkeep.ts).
- `["membership","link_token","group_purged"]` (`outbox.kind`) and the
  `OutboxRow` union (upkeep.ts).

The entry/split/event kinds already do this right (one `as const` array,
used by column + Zod). Apply the same pattern to the rest.

### 1.3 [M] Event kind → payload mapping is stated three times on the server

1. `Append` union type (events.ts) — kind groups → payload type.
2. `isEntryEvent/isMemberEvent/isGroupEvent/isLinkEvent` (schemas/ledger.ts) —
   same groups, as runtime guards.
3. `eventKinds` array (group/schema.ts) — the flat list.
(4. on the Dart side again — see §3.)

One table would drive all of them:

```ts
export const eventPayloads = {
  entry: EntrySnapshotSchema,
  member_added: MemberEventPayloadSchema, member_joined: ..., ...
} as const;
export const eventKinds = Object.keys(eventPayloads) as [keyof typeof eventPayloads, ...];
type Append = { [K in EventKind]: Written & { kind: K; payload: z.infer<typeof eventPayloads[K]> } }[EventKind];
```

(Also note the DB schema imports `EventPayload` from the wire schemas while the
wire schemas import tables from the DB schema — a type-only cycle; defining
payload shapes beside the table they're stored in removes it.)

### 1.4 [L] `BootstrapSchema` re-declares profile fields, loosely

`Bootstrap.displayName/upiVpa` re-declare `Profile` columns, and `upiVpa` is
`z.string()` rather than `UpiVpaSchema`; `isAnonymous` duplicates
`Account.isAnonymous`. Three overlapping "who am I" shapes exist: `Account`
(identity), `Profile`, `Bootstrap`. Consider `Bootstrap = { profile: Profile,
isAnonymous, groupIds }` or `ProfileSchema.pick(...)`. (Check app usage — §3.)

### 1.5 [L] `ProfilePage` cursor is two fields for one opaque token

`cursor` + `cursorId` leak the keyset to the client, which must send both back.
An opaque string cursor is the usual shape; minor.

## 2. Server: Durable Object / routes

### 2.1 [H — BUG, verified] A retried, unchanged write re-sends the previous push

`Group.upsertEntry/deleteEntry/restoreEntry/updateMember` call
`this.announce(profileId)` whenever `result.ok`, and `pendingNotices` reads
"events at `currentSeq`". A write that changed nothing spends no seq, so
`currentSeq` is the *previous* change's — its notification goes out again
(and if the previous change was someone else's, the actor exclusion is wrong
too). This is exactly the retry-after-lost-response path the idempotency
exists for.

Verified with a throwaway vitest (same fixtures as `push.test.ts`): upsert an
entry, `arranged()`, upsert the identical input again → `sent ==
["device-priya"]`, expected `[]`.

Fix: have the transactional write return the seq it spent (or `changed`) and
announce only that seq — the `changed` flag already exists on
`RosterWrite`/`EntryWrite` and is discarded by `index.ts`.

### 2.2 [M] Wire says "every field, every PUT"; the object still implements PATCH

`Group.update(patch: Partial<GroupUpdate>)`, `updateMember(..., patch:
Partial<MemberUpdate>)`, and `roster.ts` carry `?? meta.name`,
`=== undefined ? ... : ...` merging for fields the Zod schema makes required.
Likewise `join(..., options: { memberId?: string|null; displayName?:
string|null } = {})` — the "three states" the architecture doc says were
designed out. Only the **tests** pass partial objects (`object.update({ name
})`, `updateMember(id, { leftAt })` in push/activity/ledger/roster tests);
production always passes the full wire body. Type the methods with the wire
types and give the tests a small builder instead.

### 2.3 [M] Write-method boilerplate in `Group` (index.ts)

Ten methods repeat `now = nowIso(); result = attempt(() =>
this.db.transaction(...)); await this.settle(); if (result.ok)
this.announce(...); return result;`. A single private
`write<T>(body: (tx, now) => {value, seq?}, {notify})` would remove ~100 lines
and is also the natural place to fix 2.1.

### 2.4 [L] Duplicated small helpers / types inside the object

- `WriteContext` (roster.ts), `WriteContext` (ledger.ts), `InviteContext`
  (invites.ts) — identical `{ now: string; actor: MemberRow }`.
- `byMember` comparator in both ledger.ts and events.ts.
- `{ memberId: string; amountMinor: number }[]` inline in events.ts (×2) and
  the `Money` interface in ledger.ts, while `MoneyRow` exists as a wire type.
- `snapshotOf` (events.ts), `moneyOf` + `comparable` (ledger.ts) are three
  projections of one entry; `comparable` ≈ `snapshotOf` minus `deletedAt` plus
  fx + weights.
- `readEntry` duplicates `readEntries` for n=1.
- `readGroup(meta) => meta` is an identity function.

### 2.5 [L] Dead code / stale docs in the object

- `EntryWrite.unarchived` is computed and never read.
- `appendSnapshot` returns a boolean "the caller uses to decide whether to
  wake a phone" — no caller reads it (and 2.1 is the consequence).
- `createInvite(..., ttl)` / `createGroupLink(..., ttl)` + `MAX_TTL` clamp
  "because the caller supplies it" — no caller supplies it.
- `Group` class doc: "The Worker also consults D1's membership index first"
  — `api/ledger.ts` explicitly says it does not.
- `changesSince` clamps `limit` with its own `CHANGE_LIMIT {1,500,200}`, the
  same numbers the route's Zod query schema already enforces.
- `events` ordered by `rowid` within a seq though the `ordinal` column exists
  precisely to state that order.
- `groupId(tx)` falls back to `this.ctx.id.name ?? ""` — objects are always
  addressed by name, so `ctx.id.name` alone is the id; the `""` fallback would
  silently stage outbox rows for group `""`.

### 2.6 [M] The auth boundary is an allow-list of path prefixes

`app.ts` applies `requireSession` to a hand-kept list of families
(`/bootstrap`, `/groups/*`, …, `/links/:token/join`). Handlers in
`AuthedEnv` are *typed* as having a non-null `session`; a new route under a
prefix missing from the list compiles and runs with `c.var.session ===
undefined`. `createRoute({ middleware: [requireSession] })` (supported by
`@hono/zod-openapi`) or mounting the authed app under its own base ties the
guard to the route rather than to a string list.

Smaller: the two `defaultHook`s in app.ts are identical; `withSession` and
`requireSession` duplicate the session-resolution body; `AppEnv`/`AuthedEnv`
duplicate `Variables`.


### 2.7 [H — BUG, verified against docs] D1's 100-bound-parameter limit

D1 allows **100 bound parameters per query**
(developers.cloudflare.com/d1/platform/limits). Several queries bind an
unbounded list with `inArray`:

- `getProfilesByIds` accepts up to `PROFILE_PAGE_MAX = 200` ids →
  `inArray(profiles.id, ids)` **plus** the ids bound by `visibleProfiles`.
  Fails on any request above ~95 ids, by construction.
- `visibleProfiles` binds every group id the caller is in, then every
  co-member profile id. The profile feed fails for anyone sharing groups with
  ~100 other accounts, or in ~100 groups.
- `collectAbandonedGuests` selects `GUEST_BATCH = 500` ids, then
  `inArray(profiles.id, ids)` / `inArray(user.id, ids)` → fails once more than
  ~100 guests are due (i.e. exactly when the sweep matters).
- `wakeDevices`: `inArray(deviceTokens.profileId, notice.profileIds)` — bounded
  by group size, so lower risk.

The local pool (miniflare/workerd SQLite) likely does not enforce the D1 cap,
so the suite cannot catch it. Fix is idiomatic Drizzle: pass subqueries rather
than materialised arrays (`inArray(profiles.id, db.select({id:
memberships.profileId}).from(memberships).where(inArray(memberships.groupId,
db.select(...))))`), and chunk the by-ids / guest lists to ≤ 90.

### 2.8 [M — BUG, verified] Better Auth errors in `/api/identity/*` become 500s

`identity/routes.ts` never catches Better Auth's `APIError` except for the
"already claimed" case, so every other refusal reaches `app.onError` →
`500 {code:"internal", retry:"permanent"}`. Probed: `POST
/identity/email/verify` with a wrong code → **500 internal "Something went
wrong."** (no test covers a wrong or expired code). A wrong code is the most
common failure of that endpoint. Map `APIError` (status + `body.code`) to the
error envelope in one place — e.g. `app.onError` checks `instanceof
APIError` — and add `invalid_code`-style `ErrorCode`s.

### 2.9 [L] Redundant `defaultHook`s

`@hono/zod-openapi` child apps inherit the parent's `defaultHook`
(`#resolveDefaultHook` walks `#parentApp`, dist/index.mjs:46). The copies on
`authed` (app.ts), `linkRoutes()` and `referenceRoutes()` are identical to the
root's and can be deleted — `identityRoutes()` already relies on inheritance.

### 2.10 [M — verified in Hono source] `/links/:token/{placeholders,join}` resolve the session twice

`app.ts` puts `requireSession` on `/links/:token/placeholders` and
`/links/:token/join` on the `authed` app mounted at `/api`, but those routes
live in `linkRoutes()` (mounted at `/api/links`) which also runs
`withSession` and re-checks `if (!viewer) 401` by hand. Hono copies the
authed app's middleware into the parent as `/api/links/:token/join`, so both
middlewares run (hono-base.js `route()` copies every entry in `app.routes`,
including `use()` handlers): two D1 session reads for one join — the very thing the
comment in app.ts says the single `authed` app exists to prevent. Either drop
those two entries from the family list or move the two routes into `authed`.

### 2.11 [M] The push data payload is a third, untyped contract

`fcm.ts` sends `{kind, event_id, subject_id, group_id}` (snake_case, strings,
`""` for null) — a shape that exists nowhere in the OpenAPI document, is
parsed by hand on the device (see §3), and whose `kind` union is a third copy
of `NOTIFIABLE` (notices.ts) / `Notice.kind`. Declaring a `PushData` Zod
schema and registering it as a component (like the event payloads) would put
it in the generated client.

### 2.12 [L] Server odds and ends

- `identity/outcome.ts` hand-writes `Account` and the `IdentityOutcome` union
  alongside `AccountSchema`/`IdentityOutcomeSchema` — use `z.infer`.
- `reference.ts`: `currencies as Currency[]` casts the bundled JSON instead of
  `CurrencySchema.array().parse(...)` at module load; a typo in the JSON
  ships silently.
- `profilesByIdRoute` takes a comma-joined string and splits by hand; OpenAPI
  arrays (`style: form, explode: false`) are generated as `List<String>`.
- `fx/index.ts`: the `FxRate` column projection is written twice (`since`,
  `publish`); `publish` filters by `substr(as_of,1,7) = ?`, which cannot use
  the `(as_of, currency)` primary key the schema comment claims covers it (a
  `between 'YYYY-MM-01' and 'YYYY-MM-31'` range would).
- `reconcileIndex` counts distinct groups *including* left memberships to size
  its batches but pages over groups with a live membership only.
- `api/reference.ts`: up to 14 sequential `CACHE.get`s could be `Promise.all`.
- Comment density: many modules carry multi-paragraph essays per declaration
  (the AGENTS.md rule is "avoid over-commenting… explain why"). Several are
  now stale (2.5); the volume makes drift likely.

## 3. Generated client and the Dart app

### What is right (keep it)

- The chain `Zod → docs/openapi.json → dart-dio → packages/opensplit_api` is
  real, committed, and CI-enforced (`generate_api_client.dart --check`,
  `npm run openapi` diff). Enums flow from one `as const` array to a Dart
  enum with an `unknownDefaultOpenApi` sentinel, and per-class
  `disallowUnrecognizedKeys: false` keeps old apps readable by newer servers.
- The app uses generated types directly for requests, responses, enums and
  the error envelope (`ApiFailure` reads `api.Error`). There is no
  hand-written DTO layer.
- `wire.dart` is the one translation, and it is **essential, not accreted**:
  Drift tables must exist for a local-first app, Drift cannot be generated
  from OpenAPI, and the differences it bridges (nullable `seq`, `groupId`
  per row, three tables vs one nested object, calendar dates) are real.
- The freezed domain `Entry` (vs `api.Entry` vs Drift `EntryRow`) is
  justified by the same reasons: it is the assembled three-table aggregate
  with `groupId` and a nullable `seq`.

### 3.1 [H] Event payloads bypass the generated classes they were registered for

`app.ts` hand-registers `MemberEventPayload`, `GroupEventPayload`,
`LinkEventPayload` "to put a class for each in the generated client" — and
nothing in `lib/` uses them. `domain/models/group_event.dart` reads the raw
map:

```dart
String? get name => payload['displayName'] as String? ?? payload['name'] as String?;
String? get previousName => payload['previousName'] as String?;
```

A server-side rename of any payload field compiles, passes the drift check,
and silently renders "Someone" / `''`. This is precisely the place the type
chain was built to protect. Use `api.MemberEventPayload.fromJson(payload)`
etc., selected by `kind`, and delete the stringly-typed getters.

### 3.2 [M] Event kind groupings re-stated on the device (copies 4 and 5)

`DriftActivityRepository._lineFor` switches `memberAdded || memberJoined ||
memberLeft || memberRenamed → MemberChanged`, etc. — the same grouping as
`Append` and the `is*Event` guards on the server. Unavoidable in *some* form
while the generator cannot express `oneOf`, but see question Q1: a small
`x-kind-groups` / a named enum per group (`MemberEventKind`) in the contract
would let the generator carry it.

### 3.3 [M] Push data payload parsed by hand, twice

`background_handler.dart:52` and `push_service.dart:219` both read
`message.data['group_id' | 'subject_id' | 'kind']` and `fromWire` the kind;
`entry_notification.dart:119` restates the notifiable kinds (the server has
`NOTIFIABLE` in notices.ts and `Notice.kind` in fcm.ts). One parse function,
fed by a contract type (§2.11), removes three copies.

### 3.4 [M] Session/account reads bypass the contract, so server logic is duplicated in Dart

`BetterAuthService` calls Better Auth directly with raw Dio for
`sign-in/anonymous`, `get-session`, `sign-out`, `link-social`,
`sign-in/social`, and parses untyped maps (`user['id']! as String`). Because
`get-session` returns Better Auth's user, the client re-implements the
server's `toAccount` (`_accountFrom`: the `@anonymous.placeholder.invalid`
filter, dropping the guest's invented name) and `outcomeFor` (`_outcomeFor`
for the redirect path). The server's own doc for `IdentityOutcome` says the
point was to stop doing that derivation on the device.

Smallest fix: one `GET /api/identity/session → Account | null` (wrapped, e.g.
`{ account: Account | null }` per the LiveLink precedent) and
`POST /api/identity/guest → IdentityOutcome`, both returning contract types.
Then `_accountFrom`, `_realEmail` and `_outcomeFor` go away. (Alternatively
Better Auth's `openAPI()` plugin can describe its endpoints, but mixing its
schema into ours is more churn than two small wrappers.)

### 3.5 [M] Three stacked schedulers for one sync

- `SyncScheduler` — triggers (online/resume/writes) with its own `_running`
  single-flight + `_writePending` coalescing + a min-gap.
- `SyncCoordinator` (ChangeNotifier) — its own `_active` single-flight +
  `_pendingGroups/_allPending` coalescing + backoff/`nextPushAt` retry timers.
- `SyncController` (Riverpod notifier) — mirrors the coordinator's status.
- `SyncEngine._serialized` — a third serialization (`_tail` chain) inside
  `SyncGate.synchronized` (the cross-isolate lease, which is genuinely needed).

Collapse scheduler + coordinator + controller into one notifier that owns
triggers, coalescing, retry and status; keep the engine's gate. That is
likely ~200 lines and one mental model fewer.

### 3.6 [M] `RemoteLedgerApi` duplicates the generated surface to enable a second server

`RemoteLedgerApi` + `CloudflareLedgerApi` restate 17 generated methods one
to one, and exist so `test/data/fake_remote_ledger.dart` (694 lines) can
re-implement the Durable Object in Dart — seq allocation, the balance
invariant, stale-base rules, dedup, snapshots. Meanwhile `Invites` and

## 4. Tradeoffs I would like your call on

**Q1. Event payloads: keep `kind` + untyped payload, or restructure?**
The generator's `oneOf` weakness forces the `z.custom` payload today. Options:
(a) keep it, but decode with the generated payload classes (§3.1) — minimal;
(b) make `Event` carry one nullable field per shape (`entry: EntrySnapshot?`,
`member: MemberEventPayload?`, …) so the generator types it fully, at the cost
of a slightly odd wire shape; (c) switch `serializationLibrary` to
`built_value`, which supports `oneOf` + discriminator, at the cost of
`BuiltList` in every call site (the reason it was rejected).
I'd do (a) now, and (b) only if payload kinds keep growing.

**Q2. The Dart fake server.** Keep `RemoteLedgerApi` + the 694-line fake
(fast, hermetic Flutter tests; but a second implementation of the object's
rules that can drift from the real one), or drop both and run sync tests
against the live Worker (`wrangler dev`) the integration suite already
uses — or fake at the HTTP layer with a Dio adapter so the generated API is
used directly and only transport is faked? The cost is test speed/hermeticity
vs. a duplicate server.

**Q3. Request bodies from drizzle-zod (§1.1).** Deriving bodies with
`createInsertSchema(...).pick()` makes the table the single source for
column types and refinements, but ties the wire shape more tightly to the
storage shape (a column rename becomes a wire change unless explicitly
aliased). The docs chose hand-written bodies deliberately. Do you want the
stronger single-source, or the looser coupling?

**Q4. Better Auth surface (§3.4).** Wrap the remaining Better Auth calls in
`/api/identity/*` so every call the app makes is in the contract, or leave
them raw and only add `GET /identity/session`?

**Q5. Comment density.** Many server modules carry essay-length comments on
nearly every declaration; several are now stale (§2.5). Do you want a pass
that trims to "why, briefly", or is the long-form style intentional for this
project?
